# ChaosBrawl 設計草案 v0.2

> 2026-11-13。橫向帶縱深(2.5D)、最多 8 人連線的大混戰動作遊戲。只借鏡 LF2 的**戰鬥方式**,角色、美術、數值全部原創。
> 標記說明:【估算】= 推算值,需實測;【不確定】= 外部服務規格以官方為準;【待決】= 見第 8 節。

## 1. 核心戰鬥系統

### 1-1 座標與時步

- 世界座標:`x` 橫向、`z` 縱深(畫面上下)、`y` 高度(跳躍)。畫面 y = `z − y`,繪圖順序依 `z` 排序。
- 模擬固定 **60 Hz**(1 tick ≈ 16.7 ms)。LF2 原版是 30 fps,我們用 60 Hz 讓輸入更細,招式資料以 tick 計。
- 位置用**定點數**(1/256 px 的整數),不用浮點,方便重播與預測(見 6-3)。
- 舞台:寬 1600~2400 px、縱深 0~240 px;邏輯畫面 800×450(16:9,同附錄)。

| 移動參數(初值,最後調) | 數值 |
|---|---|
| 走 x / z | 2.5 / 1.6 px/tick(150 / 96 px/s) |
| 跑 x(z 可微調 1.0) | 5.5 px/tick(330 px/s) |
| 跳 | 初速 9、重力 0.5 → 滯空 36 tick(0.6 s)、最高約 81 px |
| 跑跳 | 水平速度保留 80% |

### 1-4 連段與硬直

- **命中停頓(hitstop)**:輕 3 tick、重 6 tick,攻守雙方一起停,手感關鍵。
- **受擊硬直**:輕 12 tick、重 20 tick。攻擊方的下一段在對方硬直內出手 = 連段成立。
- **取消窗**:普攻每段最後 6~10 tick 可接下一段或必殺,錯過就要等收招。
- **同招重複命中**:每個攻擊盒有 `rehit`(LF2 的 arest 概念),預設同一招對同一人只中一次,多段招才設 `rehit: 6` 之類。
- **防無限連的三道保險**:
  1. fall 值累積到 100 必倒(1-5)。
  2. 空中追打上限:被擊飛後最多再中 3 下,之後攻擊穿過、強制落地。
  3. 倒地與起身無敵 1.25 s(1-5)。

### 1-5 擊倒值(fall)與破防值(bdef)

這是 LF2 的 fall / bdefend 概念,數值自訂:

| 值 | 範圍 | 累積 | 衰減 | 到頂 |
|---|---|---|---|---|
| fall | 0~100 | 每招 `fall` 欄位(輕 20、重 35、擊倒技 100) | 20 tick 沒被打後每 tick −1 | 擊飛倒地 |
| bdef | 0~100 | 被**防住**時加招式 `bdef`(輕 15、重 35、必殺 50) | 30 tick 沒被打後每 2 tick −1 | 破防暈眩 70 tick(1.17 s) |

- 普攻 A-A-A 設計成 20 / 20 / 60:三段剛好 100 → 第三段擊倒。單挑時「三下一倒」節奏明確。
- 防禦時傷害只吃 10%(擦傷),連防 5~7 下輕攻擊會破防 → 不能一直縮著。
- **倒地無敵**:倒地 45 tick + 起身 18 tick 全無敵;起身後 12 tick 不可被抓。倒地時按左/右 = 起身翻滾(同樣無敵,換位置),避免被圍在原地。

### 1-6 攻擊判定(盒子 + Z 容許值)

每個招式格(frame)帶兩種盒子,座標相對角色腳底、朝右為正:

```json
{
  "id": 42, "pic": 18, "wait": 3, "next": 43,
  "dvx": 1.5, "dvy": 0,
  "bdy": [{ "x": -14, "y": 0, "w": 28, "h": 60 }],
  "itr": [{
    "x": 10, "y": 20, "w": 36, "h": 20, "zr": 12,
    "dmg": 30, "fall": 20, "bdef": 15,
    "kx": 2, "ky": 0, "stun": 12, "stop": 3, "rehit": 0,
    "kind": "hit"
  }]
}
```

- 命中條件:`itr` 與 `bdy` 在 x / y 投影重疊,且 `|z攻 − z守| ≤ zr`。
- `zr` 預設 **12 px**(縱深 240 的 5%),大範圍招 24~48。這是「站位比射程重要」的來源:同一條線才打得到,錯開 13 px 就能閃。
- `kind`:`hit`(一般)、`grab`(指令投,不能防)、`heal`(補隊友)、`wall`(擋射彈)、`counter`(反擊判定)。
- 射彈是獨立物件,有自己的 `bdy` / `itr`,可被攻擊打掉(互相抵消)。

### 1-7 拾取與投擲

| 道具 | 類型 | 效果 |
|---|---|---|
| 球棒 | 近戰武器 | 持有時 A 改為揮棒(傷害 ×1.5、fall 35),20 次後壞掉 |
| 平底鍋 | 近戰 / 投擲 | 揮擊有 bdef +20;丟出直線飛 |
| 紙箱 | 重物 | 持有時移動 ×0.7;丟出擊倒、會碎 |
| 石頭 | 投擲 | 小、快、傷害 40 |
| 珍奶 | 消耗品 | 拾取後喝 40 tick(可被打斷),回 HP 80 |
| 香蕉皮 | 陷阱 | 丟到地上 10 s,踩到滑倒(fall 100) |

- 拾取:站在道具上(x 距 20、z 距 12 內)按 A,8 tick。
- 投擲:持物時 A = 揮/丟(輕物揮、重物丟);跑中 A = 遠投。
- 生成:每 15~25 s 從天上掉 1 個,場上最多 6 個;舞台可定義道具權重。

|---|---|---|---|
| 關(分隊預設) | 穿過 | 穿過 | 穿過 |
| 部分 | 穿過 | 命中 | 命中 |
| 全開 | 命中 | 命中 | 命中 |

## 2. 操作

### 2-1 按鍵(每人 4 鍵 + 方向)

| 功能 | 鍵盤 P1 | 鍵盤 P2(同機) | 手把(標準配置) | 觸控 |
|---|---|---|---|---|
| 方向 | WASD | 方向鍵 | 左搖桿 / 十字鍵 | 左半畫面虛擬搖桿(8 向,死區 25%) |
| 攻擊 A | J | 小鍵盤 1 | X(□) | 右下大鈕 |
| 跳 J | K | 小鍵盤 2 | A(×) | 右下中鈕 |
| 防 D | L | 小鍵盤 3 | B(○)/ RB | 右下小鈕 |

同機最多 4 人(2 鍵盤 + 2 手把,或 4 手把);同機玩家可再加入連線房,一樣佔座位。

### 2-2 指令輸入

LF2 風格「防 + 方向 + 攻/跳」,每角色最多 6 個必殺欄位:

| 記號 | 輸入 | 慣用類型 |
|---|---|---|
| `防→攻` | D、前、A | 射彈 / 主力招 |
| `防↑攻` | D、上、A | 對空 / 輔助 |
| `防↓攻` | D、下、A | 設置 / 範圍 |
| `防→跳` | D、前、J | 突進 / 位移 |
| `防↑跳` | D、上、J | 跳躍系 |
| `防↓跳` | D、下、J | 特殊 |

- 緩衝:三個輸入在 **15 tick(0.25 s)** 內完成即可;依序按或同時按都接受。
- 「前」依角色面向判斷;`防→` 在指令表裡也可以朝後輸入讓角色轉身放招。
- 觸控輔助(預設開):**按住防 + 推搖桿 + 點攻**即成立,不必依序;另有「必殺輔助鍵」:**點一下即依角色面向自動放出該角色第一招必殺**(以角色資料 `assist` 欄位指定哪一招),不必搖桿與組合鍵;實測按鍵命中率 < 90% 時再考慮加更多專用鈕。
- 輸入在模擬端只是一個 **7 bit 位元組**(4 方向 + 3 鍵),指令判讀在模擬內做,連線只傳位元組(第 5 節)。

## 4. 模式、AI、舞台

### 4-1 模式

| 模式 | 規則 | 勝利條件 |
|---|---|---|
| 大亂鬥(預設) | 單命,HP 歸零出局,有灰血回復 | 最後存活者;時限 5 分鐘到以剩餘 HP% 判定 |
| 分隊戰 | 2~4 隊,隊伍顏色描邊;友軍傷害依 1-8 | 最後存活的隊 |
| 生存 | 1~8 人合作對抗電腦波次;**不回血**(無灰血,只靠珍奶/急救箱) | 撐過的波數;每 5 波一隻 Boss 級 AI |
| 時間賽 | 3 分鐘,倒下 3 s 後重生(重生無敵 2 s) | 擊殺數;同分加賽 30 s |

### 5-2 三種架構比較

| | (a) Firebase RTDB 中繼 | (b) WebRTC P2P,房主為中心(星狀) | (c) 自架 WebSocket(例:Cloudflare Workers + Durable Objects) |
|---|---|---|---|
| 傳輸 | REST 寫入 + EventSource 推送,JSON 文字 | DataChannel(UDP 類),二進位;不可靠通道傳快照、可靠通道傳事件 | WebSocket(TCP),二進位 |

### 5-3 定案:Firebase-only(房主權威)與可玩性估算

#### 5-3-1 資料流與路徑

每台裝置只開 **1 條 EventSource**(省連線數),寫入一律 REST(`PUT/PATCH ...json?print=silent`,不回傳內容以省下載)。

```
rooms/<code>/
  meta              模式、舞台、友軍傷害、狀態(lobby / match / result)、lastSeen、保留分鐘數
  seats/<n>         { dev(裝置 id), name, char, team, kind: human / ai / closed }
  c/                ← 客戶端監聽
    snap            { e, d: base64 快照 }(15 Hz,覆寫同一節點)
    host            { e, seat }(遷移時更新)
    ev              開局 / 結算 / 公告
  h/                ← 房主監聽
    in/<n>          { d: base64 輸入 }(覆寫同一節點)
  save              { e, seat, tick, d: base64 全狀態 }(2 Hz,沒人監聽,只在接手/回歸時 GET)
  result            結算結果
usage/<YYYYMM>      粗估流量(5-3-5)
```

- 全部是「覆寫同一節點」,儲存量固定:每房約 5 KB,1 GB 儲存額度不是瓶頸。
- `e` = 房主世代(epoch),遷移時 +1;安全規則要求 `c/snap.e == save.e`,舊房主的寫入會被拒(5-6)。
- 網路層介面維持可抽換(同 MageSandbox 覆寫 `window.Net` 的概念),將來換 WebRTC 只換實作:

```
Net.host(roomCode) / Net.join(roomCode) / Net.rejoin(roomCode)
Net.sendInput(bytes)          // 客戶端 → 房主(h/in/<n>)
Net.broadcast(snapshotBuf)    // 房主 → 全部(c/snap)
Net.save(fullStateBuf)        // 房主 → save(2 Hz)
Net.claimHost() → bool        // 遷移搶位(5-6)
Net.onInput(seat, bytes) / Net.onSnapshot(buf) / Net.onHostChange(e, seat) / Net.onPeer(seat, state)
```

#### 5-3-2 每則訊息的計費大小【估算】

Firebase 下載計費包含協定與加密開銷【不確定:以官方用量頁實測為準】。

| 訊息 | 原始 | 上線後(base64 + JSON/SSE 包裝 + TLS) | 頻率 |
|---|---|---|---|
| 快照(一般 / 最壞) | 234 / 430 B | **約 400 / 670 B** | 房主寫 15 Hz,每位客戶端各收一份 |
| 輸入(最近 8 tick + 序號) | 12 B | **約 100 B** | 有變化才送,最少 5 Hz 心跳、最多 20 Hz;激戰平均約 15 Hz |
| REST 寫入回應(print=silent,HTTP/2) | 0 | **約 50~100 B**(以 80 計)【不確定】 | 每次寫入一次 |
| save 全狀態 | 約 1 KB | 上傳不計費;沒人監聽 → 只有寫入回應 | 2 Hz |

#### 5-3-3 每房流量與頻率選擇(8 真人 = 1 房主 + 7 客戶端)

| 項目 | 計算(15 Hz) | B/s |
|---|---|---|
| 快照下載 | 15 × 400 × 7 | 42,000 |
| 輸入下載(房主) | 15 × 100 × 7 | 10,500 |
| 寫入回應 | (15 快照 + 2 save + 7 × 15 輸入)= 122 次 × 80 | 9,760 |
| **合計** | | **約 62 KB/s ≈ 225 MB/房間小時** |

| 快照頻率 | 8 真人每房間小時 | 4 真人(+4 AI) | 2 真人(+6 AI) | 其他角色平順度 |
|---|---|---|---|---|
| 10 Hz | 約 172 MB | 約 78 MB | 約 30 MB | 插值緩衝需 150 ms,快速移動略頓 |
| **15 Hz(建議)** | **約 225 MB** | **約 100 MB** | **約 36 MB** | 插值緩衝 100 ms |
| 20 Hz | 約 276 MB | 約 122 MB | 約 43 MB | 插值緩衝 75 ms |

- 單一裝置頻寬很小:客戶端下載約 6 KB/s(48 kbps)、上傳約 3 KB/s;房主上下行各約 10~20 KB/s。手機 4G 沒問題。
- 每台每秒 15~20 次 REST 寫入,依賴 HTTP/2 連線重用;M3 實測時要確認瀏覽器確實走 HTTP/2【不確定】。
- 不建議降到 10 Hz 只為省錢:省 24%,但其他角色的頓感明顯;真要省,先做快照差量壓縮(M5 之後,預估再省 30~40%)。

| 段 | 估算 |

### 5-4 延遲處理:讓 200~300 ms 仍然好玩

|---|---|
| 客戶端 3 s 沒輸入(輸入最少 5 Hz 心跳) | 房主把該座位交給 AI(普通),頭上顯示「AI 暫代」+ 斷線圖示;**座位保留到本局結束**,不會被永久收走 |
| 斷線者回來(同裝置) | 本機 `localStorage` 存 `{房號, 座位, 裝置 id}`;網路恢復或重新整理頁面後自動:GET `meta`/`seats` 確認座位的 `dev` 相符 → GET `save` 初始化完整狀態 → 監聽 `c` → 開始送輸入 → 房主收到第一筆輸入即交還控制。目標:網路恢復後 **≤ 2 s 取回**;AI 暫代期間的結果(血量、位置、擊殺)全部保留 |
| 回來時本局已結束 | 直接顯示結算畫面,再回大廳 |
| 換裝置回來 | 先不支援【待決:可加 4 碼座位 PIN】 |
| 房主斷線 | **房主遷移**(5-6),本局不中止 |
| 全部真人都離線 | 本局凍結(沒人跑模擬),`save` 保留;保留時間內任一人回來 → 他接手當房主,從 `save` 續打(5-6、5-7) |
| 直向 / 切背景 | 客戶端:同斷線規則(3 s 後 AI 暫代,回來取回);房主:超過 1.5 s 沒送快照即觸發遷移 |
| 手機省電切斷 EventSource | EventSource 內建自動重連;超過 3 s 走上面的回歸流程 |

### 5-6 房主遷移與續打快照

**續打快照(save)**

| 項目 | 內容 |
|---|---|
| 內容 | 完整權威狀態:tick、亂數狀態、模式計時與分數、擊殺歸屬;每角色完整狀態(位置、速度、招式格與剩餘 wait、HP/灰血/MP、fall/bdef 與衰減計時、無敵與硬直計時、rehit 表、持物);道具、射彈、陷阱;座位與 AI 等級。AI 內部思考狀態不存(接手後重新判斷) |
| 大小【估算】 | 一般約 700 B、最壞約 1.1 KB;base64 後 ≤ 1.5 KB |
| 頻率 | **2 Hz(每 30 tick)**。1 Hz 最壞回溯 60 tick 太多;4 Hz 收益小,且多吃每秒寫入上限 |
| 成本 | 上傳不計費、沒人監聽;只有寫入回應約 0.6 MB/房間小時,可忽略;儲存每房 ≤ 1.5 KB |

**遷移流程**

1. **偵測**:客戶端 1.5 s(約 22 則快照)沒收到快照 → 畫面凍結,顯示「房主連線中斷,接手中…」;停止自身預測,避免越跑越歪。
2. **接班順序**:房主每 5 s 在 `c/ev` 公布 `succ`(候選座位):電腦 > 平板 > 手機、前景、RTT 低者優先;AI 座位不列入。
3. **錯開**:第 k 順位等 k × 0.7 s 再動作,減少同時搶。
4. **確認房主真的掛了**:GET `save`(帶 ETag)→ 等 1 s → 再 GET;ETag 沒變(房主活著每 0.5 s 會改 `save`)才繼續;變了 = 是自己網路的問題,回到等待。
5. **搶位**:對 `save` 做條件寫入(`if-match` ETag),`e + 1`、`seat` = 自己。成功 = 新房主;失敗 = 別人搶到,等新房主的快照。
6. **防雙房主**:安全規則要求 `save` 寫入的 `e` 不得小於現值、`c/snap.e` 必須等於 `save.e`。舊房主若只是延遲,回來後寫入被拒 → 自動降為一般玩家,走 5-5 回歸。
7. **續打**:新房主以 `save` 為底,疊上自己收到的最新快照(比 `save` 新 ≤ 0.5 s)的位置、招式格、HP/MP/fall/bdef → 實際回溯通常 **< 5 tick**;若合併失敗(tick 對不上)改用純 `save`,回溯 **≤ 36 tick(0.6 s)**。舊房主的角色交 AI 暫代,回來可取回。
8. **恢復**:新房主改監聽 `h`、寫 `c/host` 通知全員;全員顯示 1 s「繼續!」後開跑。凍結期間模式計時不走。
9. **空窗期**:偵測 1.5 s + 錯開 0~1.4 s + 確認 1 s + 載入與倒數約 1.3 s ≈ **4~5 s**【估算】。期間全員凍結,不影響公平。偵測若縮到 1.0 s,Wi-Fi 抖動容易誤判(第 4 步雖能擋,但會頻繁凍結畫面),不建議。
10. **房主主動離開**(按離開):先寫最後一次 `save` 並在 `c/host` 指定接班者,省掉偵測與確認,中斷約 1.5 s。
11. 連續遷移同流程,`e` 繼續遞增。新房主是手機也照跑,但 `succ` 排序讓電腦優先。

### 5-7 房間流程與存活時間(沿用 MageSandbox 規則,依 v0.2 調整)

1. 封面 → 創建房間 / 進入房間。
2. 創建:產生 4 碼房號,可選密碼(雜湊存庫),分享 `?room=XXXX` 連結或 QR Code(沿用自寫 QR)。
3. 大廳:8 個座位,每人選角色與隊伍;房主可把空位設「電腦(等級)」或「關閉」;房主選模式、舞台、友軍傷害、房間保留時間。
4. 加入者寫入 `seats/<n>`(帶裝置 id),監聽 `c`;開局後即依 5-3-1 收送。不需要 P2P 交握。
5. 建房分兩步寫(先房間索引與 meta,再 seats),同 MageSandbox 規則限制。
6. Firebase:**新開獨立專案**,RTDB 建在 asia-southeast1;資料庫網址是公開識別碼,不放任何私密金鑰。開專案需使用者本人帳號操作。

**存活時間**(不依賴 Firebase 過期查詢清理,MageSandbox 經驗:會被規則擋;一律「建房時檢查舊資料是否過期,過期即覆寫」)

| 房間狀態 | 心跳 | 視為過期 |
|---|---|---|
| 大廳(未開局) | 每人 30 s 寫 `lastSeen` | 5 分鐘沒有心跳 |
| **對戰中** | 房主每 30 s 寫 `lastSeen` | **全部真人離線超過 30 分鐘**(= 房主 `lastSeen` 超過 30 分鐘);之前任一人回來都能續打 |
| 結算後 | 同大廳 | 5 分鐘;結果保留到房號被覆寫 |

N = 30 分鐘的理由:家用斷線常見的 Wi-Fi 重連 10~60 s、數據機或路由器重開 2~5 分鐘、ISP 短暫中斷 5~15 分鐘,30 分鐘都涵蓋;保留成本只有約 5 KB 儲存、零下載,拉長沒有費用代價;再長的壞處只是房號佔用較久、回來時人多半已散。房主可在大廳改為 10 / 30 / 60 分鐘,預設 30。

### 5-8 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| Spark 下載額度用完 | 當月資料庫停用,連大廳都不能用【不確定】 | 用量計 + 90% 軟上限;超出常態用量時升 Blaze(**待使用者決定**,見第 8 節) |
| 實際延遲高於估算(Wi-Fi 抖動、4G) | 被打吃虧感變重、白打火花變多 | M3 第一步先做連線實測;不達標回第 8 節討論 WebRTC 升級 |
| REST 寫入回應的計費比估算高 | 費用上升(寫入回應約佔 16%) | 實測;若偏高,輸入改每 3 tick 批次送(最多 20 Hz → 固定 15 Hz) |
| 每秒寫入上限(約 1,000 次/資料庫)【不確定】 | 同時約 8 個滿房 | 家用足夠;要公開配對才需 Blaze 多實例分流 |
| 遷移造成雙房主 | 狀態分岔 | 安全規則以 `e` 擋舊房主寫入(5-6 第 6 步) |
| 手機房主切背景 | 遷移造成 4~5 s 中斷 | 建議電腦開房;`succ` 電腦優先 |
| 預測修正太頻繁 | 自己角色抖動 | 平滑拉回;M3 記錄每分鐘修正次數與平均距離 |
| 房主作弊(改本機模擬) | 朋友局可接受 | 不處理,只記錄 |

### 5-9 未來升級:WebRTC(非主方案)

若實測延遲不達標、或用量大到 Blaze 月費不划算,可把「快照與輸入」改走 WebRTC DataChannel(房主為中心的星狀),Firebase 只做大廳與交握:按鍵到命中可降到 50~100 ms、對戰流量不經 Firebase(幾乎零費用);代價是約 10~20% 的連線因對稱型 NAT 直連失敗,仍需 Firebase 中繼備援【估算】。因 `Net` 介面可抽換,上層模擬、預測、遷移流程不用改。需使用者同意才啟動。

## 6. 技術建議

### 6-1 繪圖:Canvas 2D(建議)

| | Canvas 2D | Three.js |
|---|---|---|
| 外部程式庫 | 0 | 約 600 KB,需下載(權限問題) |
| 2.5D 精靈圖 | 原生適合,依 z 排序直接畫 | 要用平面貼圖模擬,繞路 |
| 效能 | 8 角色 + 50 特效,中階手機 60 fps 無壓力【估算】 | 足夠但耗電較高 |
| 美術流程 | 2D 圖直接用 | 若做 3D 模型,美術成本高很多 |

結論:Canvas 2D。模擬層不碰繪圖,將來真要換渲染器只換 `render/`。

### 6-2 固定時步

- `requestAnimationFrame` 累加器:每累積 16.67 ms 跑 1 tick,單幀最多補 4 tick(防切回分頁暴衝);繪圖用上下兩 tick 內插。
- 房主模擬不依賴畫面更新率;切背景時改用 `setInterval` 維持(瀏覽器會降頻,所以仍建議房主不切背景;若快照中斷超過 1.5 s 會觸發房主遷移,見 5-6)。
- 房主遷移與回歸都從 `save` 還原狀態,所以 `sim/` 要提供「全狀態序列化 / 還原」,且還原後繼續跑的結果要與不中斷時一致(6-3 的雜湊測試涵蓋)。

### 6-3 決定性與重播

- 連線不需要決定性(房主權威),但仍建議做:定點數、種子亂數(房主每局給種子)、固定處理順序(依座位號)。
- 好處:(1)自身預測與房主結果一致,修正少;(2)**重播** = 種子 + 全員輸入,8 人 × 60 B/s = 480 B/s,3 分鐘約 86 KB,壓縮後 10~20 KB【估算】;(3)無頭測試:同輸入跑兩次,比對每秒狀態雜湊,抓 bug。

## 附錄:手機版與橫向限定(2026-11-13 決議)

**決議**:只做橫向。直向不開發版面,偵測到直向時顯示「請把手機轉橫」提示,不進遊戲畫面。

### 直向處理
- PWA manifest 設 `"orientation": "landscape"`(安裝到主畫面後 Android 會直接鎖橫向)。
- 全螢幕時呼叫 `screen.orientation.lock('landscape')`。【限制】iOS Safari 不支援鎖定,所以不能只靠這招。
- 一律加 CSS 後備:`@media (orientation: portrait)` 蓋上全螢幕提示層(轉向手機圖示 + 文字),提示層下方的遊戲不接受輸入。
- 連線中不能暫停別人的遊戲。建議:直向期間角色維持站立或防禦,超過 3 秒沿用既有的斷線規則由 AI 接管,轉回橫向後立即取回。單機模式則直接暫停。

### 畫面與版面
- 邏輯解析度固定 16:9(建議 800×450),等比縮放填滿螢幕,多出的邊用背景延伸;不同比例手機(18:9、20:9)左右留黑邊或延伸舞台背景,不拉伸。
- 避開瀏海與圓角:使用 `env(safe-area-inset-*)`,按鈕放進安全區內。
- 觸控配置:左下虛擬搖桿(含上下走位);右下 攻擊、跳、防禦 三鍵,必殺輔助鍵(點一下自動放第一招必殺)在三鍵上方。按鈕直徑建議 ≥ 56 px(約 9 mm),支援多點觸控(搖桿與按鍵同時按)。
- 8 人同屏時血條縮成上方一排小型條(2 排 × 4),不遮擋戰場;手機上預設隱藏角色名,只顯示隊伍色圈。
- 進入遊戲時要求全螢幕(需使用者點一下);禁止縮放、下拉重新整理、長按選單;使用 Wake Lock 避免螢幕變暗。

### 效能目標(待實測)
- 模擬 60 Hz 不變;繪圖在中低階手機可降為 30 fps,不影響連線同步。
- 目標:中階 Android 手機 8 人同屏穩定 ≥ 30 fps。若不足,依序降低:粒子特效數量、陰影、背景視差。
- 這是推估,M1 做出雛形後用真機測。

### 對路線圖的影響
- M1 起就要有觸控操作與橫向提示層,不留到最後補。
- 不再開發直向版面,省下一套 UI 設計與測試。
