## 0. 一頁式摘要

**使用者已定案的方向**
1. 右下大圈 = 純「滑動出招區」(點一下不出任何東西);普攻改為一顆小按鈕;**必殺技與最強必殺技只能用手勢發動**(預設無一鍵按鈕)。
2. 手勢含直線與弧形(半月),同類招式同一種手勢形狀,舉一反三。
3. **取消跳躍**,改用「月步」:前衝(可連踏 2~4 段追人)、後滑(可連用逃跑)、縱步(上下閃)。
4. 普攻大幅降傷,不能「普攻一招鮮」;必殺技是主要輸出。

**我的推薦(一句話版)**
- 手勢:一筆畫完、放開才判定;只比對「目前角色」的 8 個手勢(4 招 + 前衝/後滑/縱步上/縱步下),誤出招率低。
- 10 種手勢家族(射擊 = 上弧往回拉再往前送、上挑 = 上弧往前、下盤 = 下弧…),MP 招 1~3 筆、最強 1~4 筆(約 0.35~0.7 秒)。
- 取消跳躍 **全遊戲生效**(含鍵盤),鍵盤 K 改成「步 / 技」鍵,連線公平。
- 月步用獨立「步力條」(100,前衝 25、後滑 20、縱步 15,每秒回 30),不吃 MP。
- 普攻 ×0.4(整套連段 40 傷 ≈ 血量 6.7~9.3%)+ 同目標連續普攻遞減;MP 回復 6→14/秒、開局 200→300、必殺消耗 ×0.7、必殺傷害 ×1.2。
- 推算:混合打法擊殺 500 血約 30 秒;純普攻(完美命中)約 100 秒以上 → 一招鮮行不通。
- 一鍵必殺鈕:只在單機 / 練習場可於設定開啟(預設關),連線對戰一律沒有。

## 1. 手勢文法

### 1-1 基本規則

- **起筆**:手指按下的位置必須在「手勢圈」內(見第 6 節版面,直徑 150px,判定區再外擴 10px)。
- **一筆畫**:手指不離開螢幕畫完整個手勢;**放開時才判定**。放開前顯示軌跡,不出招。
  - 理由:可以接受前綴相同的手勢(例 `○` 與 `○→`),判定時機固定、好預測;放開的延遲幾乎是 0(滑完自然放開)。
- **畫出圈外繼續算**:按下後用 `setPointerCapture`,手指滑到任何地方都屬於這一筆(經過普攻 / 防鈕也不會觸發它們)。手指滑出螢幕邊緣 → `pointercancel` → 取消,不出招。
- **點一下**:總位移 < 10px 且 < 450ms → 什麼都不做(教學期間顯示一次小提示「普攻在左邊小鈕」)。
- **按住**:位移 < 10px 持續 ≥ 600ms → 記為 `●`(只有騎玉最強用到),圈上出現蓄力環。
- **前 / 後**:以「按下那一刻的角色面向」換算;面向左時所有左右方向鏡像。上下不鏡像。
- **時間上限**:整筆(不含 `●`)MP 招 ≤ 1200ms、最強 ≤ 1800ms,超過判「太慢」。不設單筆時間限制。
- **比對對象**:只跟「目前角色」的 8 個手勢比(3 招 + 最強 + 前衝 + 後滑 + 縱步↑ + 縱步↓)。別的角色的手勢不會誤出。

### 1-2 尺寸推算依據

- 手機橫向:CSS 高度約 360~430px(寬 740~930)。一般手機約 160 CSS px/吋 → 1 CSS px ≈ 0.16mm。
- 拇指接觸面約 7~10mm ≈ 45~60px;舒適的拇指快滑一筆約 8~12mm ≈ 50~75px。
- 現有攻鈕直徑 84px(`css/main.css` `.b-atk`)。要畫半月,弦長至少 36px(見下方弧形判定),84px 的圈太擠 → 手勢圈放大到 150px,並允許畫出圈外。

### 1-3 原子筆劃(token)

| token | 名稱 | 判定 |
|---|---|---|
| `F` `B` `U` `D` | 前 / 後 / 上 / 下 直線 | 累積轉角 ≤ 35°、長度 ≥ 24px;方向落在 4 向 ±35° 內;35°~55° 的斜向視為模糊 → 不認 |
| `AU>` `AU<` | 上半月 往前 / 往回 | 累積轉角 130°~250°、路徑 ≥ 50px、弦長 ≥ 32px、弦與水平夾角 ≤ 40°、弧的中點在弦上方 |
| `AD>` `AD<` | 下半月 往前 / 往回 | 同上,中點在弦下方 |
| `AF↓` `AF↑` | 前半月 由上往下 / 由下往上 | 弦與垂直夾角 ≤ 40°,中點在弦的前方 |
| `AB↓` `AB↑` | 後半月 由上往下 / 由下往上 | 中點在弦的後方 |
| `C1` | 一圈 `○` | 同一旋轉方向累積 290°~460°(順逆時針皆可) |
| `C2` | 兩圈 `◎` | 同向累積 620°~860° |
| `C8` | 8 字 `∞` | 兩段相反旋轉,各 250°~460° |
| `H` | 按住 `●` | 位移 < 10px 持續 ≥ 600ms |

60°~129° 的平順轉彎(四分之一圓)**不認**,回饋「弧度不夠,畫成半圓」。不收四分之一圓是為了讓「轉角」和「半月」之間有明顯間隔,降低誤判。

### 1-4 辨識演算法(放在 `js/ui/gesture.js`,純函式,可在 node 測)

1. 收點:`pointermove` 加上 `getCoalescedEvents()`,記錄 (x, y, t)。
2. 重新取樣:每 5px 一點;3 點移動平均去抖。
3. 算每段方向角,得到逐點轉角序列。
4. **切段**:
   - 轉角:15px 路徑內轉角 ≥ 55° → 切開(例:↑ 接 ↓ 的折返、↑ 接 → 的直角)。
   - 曲率改變:轉彎區之後接 ≥ 24px 幾乎不轉的直線 → 切開(例:`◠` 畫完接著往下拉,或 `○` 畫完往前推)。
   - 起頭與結尾 < 12px 的小段丟掉(手指剛按下 / 放開的抖動)。
5. 每段分類成上表 token;無法分類 → 失敗。
6. 依面向把 F/B、弧的方向轉成相對方向,得到 token 序列。
7. **比對**:
   - 完全相同 → 命中。
   - 不同 → 「寬鬆比對」:token 序列的編輯距離(替換相似 token 成本 0.5,例如 `C1` vs `C2`;其他 1)。最佳 ≤ 1 且第二名至少多 1 → 命中;否則失敗。只有 MP 招與月步用寬鬆比對;**最強只接受完全相同**(避免誤放大招)。
8. 輸出:`{ id: 'sp_fwd_atk' | 'ultimate' | 'step_f' | 'step_b' | 'step_u' | 'step_d', ok, reason, nearest }`。

前綴衝突檢查:每個角色的 8 個手勢序列兩兩編輯距離 ≥ 2(或差異是 `C1/C2` 這種要畫很多才會錯的),開發時用單元測試驗證(第 9 節)。

### 1-5 送進遊戲(不改模擬層的判讀,確定性不變)

- 辨識只在本機;結果轉成「逐 tick 的輸入位元組」放進 `input.queueMacro('P1', bytes)`,跟現在的必殺按鈕、AI 用同一條路。連線時送出去的仍是輸入位元組,房主與各端用相同輸入跑模擬 → 確定性不受影響。
- MP 招:`commandMacro(cmd, face)`(`js/sim/command.js`,防 + 方向 + 攻/跳,4 tick)。
- 最強:`ULT_MACRO`(防 + 攻 + 跳)。
- 月步:新的第 8 個輸入位元 `BIT.STEP = 128` + 方向(見第 4 節)。輸入本來就是 1 byte(`net/codec.js` 的 `encodeInput` 用 `Uint8Array`,hist 也逐 byte 存),**不用改連線格式**。
- **送出前的本機檢查**:MP 不足 / 爆氣未滿 → 不送,直接給回饋(第 2 節)。
- **送出時機緩衝**:若角色正處於不能出招的狀態(普攻非取消段、受擊硬直),觸控層保留這個指令最多 200ms,每 tick 檢查一次本機角色狀態(單機讀 `world`,連線讀 `online.pw` 預測世界),一能出就送;超過 200ms 丟棄並顯示「時機不對」。只影響「什麼時候送輸入」,仍是確定性的。

### 1-6 時間估算(熟練者;新手約 ×1.8)

推估依據:拇指快滑 40~60px 約 80~100ms;直線折返多 40ms;半月(路徑約 80px)約 150ms;一圈約 280ms;兩圈約 550ms。

| 手勢 | 熟練 | 新手 |
|---|---|---|
| 一筆直線(月步) | 90ms | 160ms |
| `◠(→)` / `◡(→)` / `⊃` / `⊂` | 150ms | 270ms |
| `←→` / `→←` / `↓→` | 220ms | 400ms |
| `◠(←)→`(射擊) | 280ms | 500ms |
| `○` | 280ms | 500ms |
| `↑↓↑` | 350ms | 630ms |
| 最強 3~4 筆(`↑↓↑↓`、`↑○→`、`⊃→←`…) | 350~550ms | 650~1000ms |
| `◎→` / `↑◎` | 680ms | 1200ms |
| `●→` | 690ms(含 600ms 蓄力) | 同左 |

對照:舊的直接按鈕 = 手指點到 + 巨集 3 tick ≈ 50~70ms。手勢慢 100~500ms(6~30 tick)。這是刻意換來的「有學問的操作」,也是平衡的一部分(第 7 節普攻與 MP 經濟一起算過)。

### 2-3 角色內衝突檢查(人工初查,開發時以單元測試覆核)

- 每角色 8 個序列兩兩編輯距離:最小值出現在「`○` vs `○→`(柯南)」「`○` vs `○↑↓`(漫漫)」「`◠(→)` vs `◠(→)◡(→)◠(→)`(帆帆)」「`⊃(↓)` vs `⊃(↓)→←`(關羽)」,都是前綴關係;因為**放開才判定**且最強只接受完全相同,不會互相誤出,只會在「最強沒畫完就放手」時變成小招(或寬鬆比對失敗、不出招)。
- 單筆 `→`(前衝)vs 騎玉 `●→`:靠 600ms 蓄力環區分。風險:騎玉玩家停在圈上 0.6 秒再前衝 → 若爆氣滿會放最強。對策:蓄力環亮起時有聲光提示,不想放就放開重按。列為待確認 #10。
- 原本設想 連打 = `→←→`,與 突進 `←→` 只差一筆、漏畫第一筆就誤出,改成 `↑↓↑`;閃反 原本 `↓↑` 與 `↑↓↑` 只差一筆(騎玉兩招都有),改成 `⊂(↓)`。

### 2-4 誤判率推估

假設每種原子筆劃的辨識成功率(熟練 / 新手,推估):直線 98% / 95%、折返轉角 98% / 94%、半月 94% / 85%、一圈 93% / 82%、兩圈 88% / 75%、8 字 85% / 65%、按住 99%。序列成功率 = 各筆相乘。

| 手勢 | 熟練 | 新手 |
|---|---|---|
| 月步(一筆) | 98% | 95% |
| `◠(→)` `◡(→)` `⊃` `⊂` | 94% | 85% |
| `←→` `→←` `↓→` | 94% | 85% |
| `◠(←)→` | 90% | 76% |
| `○` | 93% | 82% |
| `↑↓↑` | 92% | 80% |
| 最強 3~4 筆 | 82~88% | 60~72% |
| `●→` | 97% | 93% |

- **失敗 ≠ 誤出**:失敗只是不出招(不扣 MP)。誤出成別招(錯招)需要剛好落在別的手勢上,因為每角色只有 8 個且彼此距離 ≥ 2,推估 ≤ 2%。
- 寬鬆比對可把 MP 招熟練成功率再提高約 3~5 個百分點(推估),代價是錯招率 +約 1%。
- 驗收:練習場紀錄「想畫的招(練習模式指定) vs 辨識結果」,目標熟練 10 分鐘後 MP 招 ≥ 90%、最強 ≥ 80%、錯招 ≤ 2%。達不到就放寬角度 / 長度門檻。

### 2-5 長手勢評估(使用者例:↑↑↓↓←←→→)

一筆畫中「↑↑」跟一條長的「↑」無法分辨,必須放開再按 → 8 次按放 ≈ 8 × (90ms 滑 + 120ms 重按) ≈ 1.7 秒;成功率 0.97^8 ≈ 78%(熟練)、0.95^8 ≈ 66%(新手)。實戰 1.7 秒幾乎一定被打斷,不採用;可在練習場做「隱藏彩蛋」。所以最強定為 1~4 筆、0.35~0.7 秒,用「形狀複雜度」而不是「筆數」表現難度。

### 4-2 全遊戲還是只有手機?

- **只有手機**:鍵盤玩家能跳(跳攻、閃大地震、空中躲射彈),手機玩家不能 → 連線對戰手機明顯吃虧;說明書、AI、招式反制要寫兩套。
- **全遊戲(推薦)**:模擬層加規則旗標 `rules.noJump = true`(預設開,寫在 world 裡,連線各端一致)。鍵盤 K 改成「步 / 技」鍵:
  - K + 方向 = 月步(K 單按 = 前衝;K + 後 = 後滑;K + 上 / 下 = 縱步)
  - 防 + 前 / 上 / 下 + K = 原本 D>J 必殺(不變)
  - 防 + 攻 + K 或 U = 最強(不變)

### 4-3 月步規格

全角色共用同一套數值(第一版不分角色,之後可依角色微調)。tick = 1/60 秒。

| 項目 | 前衝 | 後滑 | 縱步(上 / 下) |

| 手機手勢 | 一筆 `→` | 一筆 `←` | 一筆 `↑` / `↓` |
| 鍵盤 | K(或 K + 前) | K + 後 | K + 上 / 下 |
| 起步 | 2 tick | 2 tick | 2 tick |
| 移動 | 8 tick,共 150px(約 18.8 px/tick,跑步的 3.6 倍) | 10 tick,共 110px,面向不變 | 8 tick,縱深 z 移動 60px |

| 每段週期(連踏) | 10 tick → 平均 15 px/tick | 12 tick → 平均 9.2 px/tick | — |
| 連續上限 | 4 段(600px,40 tick ≈ 0.67 秒) | 4 段(440px,48 tick) | — |

| 可用狀態 | 待機、走、跑、普攻取消段、防禦中不行(防 + 左右是翻滾) | 同左 | 同左 |

**距離推算依據**:跑速 4.4~6.0 px/tick(呂布最慢、小孫最快,平均約 5.2);舞台寬 2000、縱深 240。前衝 2 段 = 300px 約 0.33 秒(使用者要求 0.25~0.4 秒縮短 250~350px);後滑 2 段 = 220px 約 0.4 秒(要求 200~300px)。縱步 60px 大於多數射彈縱深判定 zr 12~24 + 身體寬度,足以錯開。

**步力條**:100 滿;停止月步 0.4 秒後每秒回 30(空到滿約 3.7 秒)。顯示在 HUD 血條下(青色細條)。
- 不吃 MP 的理由:MP 是必殺經濟(第 7 節),月步若吃 MP 會讓「追上了卻沒 MP 出招」,兩邊互相卡。
- 不採「每段遞增消耗」:平坦消耗 + 上限 4 段,玩家好算(滿條 = 4 次前衝 / 5 次後滑,但連續上限 4)。

**與自動跑的關係**:搖桿推到最外圈仍是自動跑;跑步中畫 `→` = 從跑步直接接前衝(不必先停)。月步結束若搖桿仍在外圈,恢復跑步。

### 4-4 追擊 vs 逃跑推算(連續前衝 vs 連續後滑)

設雙方步力都滿;逃跑者看到對方起步後反應 15 tick(0.25 秒,推估人類反應)。

- 追擊者:t = 0~40 前進 600px,之後收招 16 tick(t = 56 才能動)。
- 逃跑者:t = 15 開始後滑,每 12 tick 110px;到 t = 40 已滑約 230px;t = 63 滑完 440px,收招到 t = 71。
- t = 40 時兩人距離 = 初始距離 d − 600 + 230 = **d − 370**。
- 追擊者在最後一段取消進招式:
  - 近戰招(有效距離約 80px):**d < 450 追得到;d ≥ 450 逃得掉**(逃跑者預判先動、反應 0 時門檻降到約 310)。
  - 射彈招(射程 300~700px):d − 370 仍在射程內 → 後滑逃不掉,要用**縱步錯開 z** 或防禦。這正好呼應「遠距離招式不必縮短射程」,反制交給縱步。
- 追擊者全力 4 段後步力歸零、收招 16 tick;逃跑者還剩 20 步力(1 次後滑或 1 次縱步)。**追空的一方有 16 tick 破綻**,逃跑者可在 t ≈ 71 起反打(前衝 1 段 + 快招,約 12 + 8 tick)。

**結論**:近距離(< 約 300~450px)追擊者佔優;遠距離逃跑者佔優且追擊者用光步力後會被反打。不會只有一方贏。

平衡旋鈕(實測後再調):前衝距離 150 ±20、後滑距離 110 ±15、收招 16 tick、步力回復 30/秒。

### 6-2 人體工學評估

- 右手拇指一指負責三樣:手勢圈(最常用,放在拇指自然停靠的右下)、普攻、防。三者中心距 130~140px,拇指移動 Fitts 估算約 150~250ms。

- 影響:手機很難做「普攻 → 取消進必殺」的真連段。attack2 取消窗只有最後 10 tick(167ms),移指 200ms + 半月 150ms ≈ 350ms 已超過一段普攻總長 300ms,所以普攻後的必殺是「接在後面」而不是「取消」。對策:不把普攻 → 必殺連段當成手機的設計目標;普攻用途是牽制、擊倒、製造距離;必殺在對手起身、月步貼近時放(月步取消進招式取代普攻取消)。鍵盤仍可做真連段 → 這是鍵盤與手機的已知差距,靠普攻降傷縮小(普攻占總傷害少,連段差距的影響也小)。
- 防 + 手勢:手勢巨集本身會帶「防」位元,不需要手指按防。

### 7-3 驗收條件(硬限制:不可普攻一招鮮)

**(a) 傷害上限**:普攻單下 ≤ 16(籠卷血量的 3.7%);整套連段 40 = 血量 6.7%(呂布)~ 9.3%(籠卷)≤ 10%。✔

**(b) 連段遞減**:每個被打者記錄「普攻命中計數」與最後一次被普攻打中的 tick;3 秒(180 tick)內沒再被普攻打中就歸零。第 1~3 下 ×1.0、第 4~6 下 ×0.5、第 7 下起 ×0.25(最少 1)。必殺與最強不計入、也不受影響 → 「普攻一套後接必殺」完全不打折。

**(c) 普攻回 MP 上限**:只有計數第 1~3 下各 +4,同目標 3 秒內最多 +12;被防 0。純普攻每秒最多約 4 MP(一套 1 秒、但擊倒後起身約 1 秒),相當於 20 秒才多一招 → 不會形成「普攻 → 回 MP → 放招」無限循環。

**(d) 防禦剋普攻**:普攻被正面防住 0 傷害、bdef 只累積一半(破防需要約 11 下普攻,原本 6 下)。

**(e) AI 與單機**:
- AI 現在以普攻為主(`ai.js` LEVELS 的 `atkCd`、`chain`),降傷後 AI 會變很弱。調整:`special` 機率 新手 0.05→0.25、普通 0.3→0.55、困難 0.6→0.8、魔王 0.9→0.95;`chain`(連段續打機率)各降約 0.2;MP 變便宜後 AI 自然更常放招。
- 練習場木樁不受影響;puncher 的普攻傷害跟著降(練習用,沒差)。
- 鍵盤玩家同樣套用(全遊戲規則)。

### 7-4 TTK 推算(1 對 1,以 500 血為例)

前提(推估):實戰命中率必殺 50%、普攻連段 60%;灰血(傷害 30% 變灰血,3 秒沒挨打就每秒回 10)使實際所需傷害約多 15%。

|---|---|---|---|---|---|
| 混合(必殺 + 普攻 + 最強) | 必殺 60 × 0.5 = 30 + 普攻 40 × 0.6 = 24 | 約 15.4(加最強後約 17) | **約 30 秒** | 約 26 秒 | 約 36 秒 |

| **只用普攻(完美 100% 命中)** | 一套 + 擊倒起身週期 ≈ 2.05 秒,遞減穩定在 ×0.25 → 每套 10 | 約 4.9 | **約 102 秒** | 約 88 秒 | 約 122 秒 |
| 只用普攻(等遞減歸零再打) | 一套 40 / (2.05 + 3) 秒,但等待期對手灰血回復 | 約 7.9 → 扣灰血回復約 6 | 約 83 秒 | 約 72 秒 | 約 100 秒 |

## 8. 跟電腦版鍵盤的關係

- **滑動手勢只在觸控**;鍵盤仍用「防 + 方向 + 攻 / K」指令(招式代號與判讀 `detectCommand` 不變)。
- 全遊戲共同改動:取消跳躍(K 改步 / 技鍵)、月步、普攻降傷與遞減、MP 經濟。
- 招式表(`moves.js`)依裝置顯示:鍵盤 = 按鍵指令,手機 = 手勢動畫。

### 9-4 實作順序建議
1. 先做辨識器 + 練習場畫軌跡(不接戰鬥),讓使用者實機畫畫看手感 → 確認尺寸門檻。

3. 最後接 UI、說明書、教學。

### 9-5 尚未驗證 / 待查
- 人因數字(滑動速度、辨識成功率、反應 15 tick)皆為推估,須練習場實測。
- 小志 dragon 射彈的縱深判定 `zr`、藤蔓 trap 的判定寬度,影響第 4-6 節反制可行性,實作時讀資料確認。
- 必殺多段招的「單目標實際傷害」受擊退與 hitstop 影響,本文 TTK 用單段中位數約 50(×1.2 = 60)估算,平衡回合以模擬實測為準。
- 現有 `commandMacro` 的第一個 tick(防 + 前)在站立時會先進入翻滾,第 3 tick 才由翻滾的 `specialCancel` 取消成必殺(角色會先滑 8px)。這是現況行為,手勢沿用不受影響;若要更乾淨可另外處理。
